# The access model

How does the syncplane engine decide what a caller can read and write from rows in a workspace? This document explains how access rules behave, why you declare rules in the schema instead of in application code, and what the access model costs.

## Why access is declared

Application hooks such as `ReadFilter` evaluate access one row at a time, and only from that row. A rule such as "a task is readable when its project grants it" depends on another row. An application hook must load the project grants before the read starts, and that grant set can change while the read runs.

When an access parent changes, the visibility of every child row changes without changes to the child rows. An **access parent** is a row that another row references for access rules. For example, when you remove a member from a project, the visibility of every task below that project changes, but no task row changes. The engine cannot detect this change from external code, so the application must touch every task row or bump the filter epoch.

The access model puts the rules in the schema. The engine knows which rows grant access, which reference connects a row to its access parent, and which permissions each entity requires. With this information, the engine finds rows when their visibility changes, reads grants in the same snapshot as rows, and checks writes against parent rows inside the write transaction.

## Grants, roles and anchors

A **grant row** is a row that assigns one role to one subject (a user or a team). A **role** is a named set of permissions. A **permission** is an opaque string that authorizes an operation. An **anchor** is the row where a grant applies, or the **workspace root** when the grant entity declares no `parents` in its `access`. The workspace root is the top-level container of all data in a workspace, where access applies to all rows.

A permission held at an anchor applies to the anchor row and to every row whose access parent points at the anchor. With an org schema:

- An `OrgMember` grant has no parent, so its role applies at the root and reaches every row.
- A `ProjectMember` grant points at one project, so its role applies to that project and to the tasks and members below it.
- A `Task` points at its project, so a caller reads it when it holds `view_tasks` at the root or at that project.

What a caller holds is the union of every grant row that names one of its subjects, plus the root roles from `WithCallerAccess`. Access only grows by adding grants. There is no deny rule: a rule that removes access would make access non-monotonic, and the engine could no longer compute changes from added and removed anchors. Application hooks run after the model and can only narrow what it allows.

A role can **include** other roles of the same grant entity, and grants their permissions as well as its own. Registration expands the includes, so at runtime a role is one flat set of permissions. Cursor records, the `CallerAccess` summary, and write checks never see an include. A change to an included role reaches clients like any other change to what a role grants. An include is limited to the roles of one grant entity. The roles of one entity are usually one ladder, such as reader, writer, and admin. This limit keeps each grant entity's roles readable and checkable by themselves: a change to one grant entity's roles never changes what another entity's roles grant. A role of one entity that needs the permissions of a role of another entity lists them directly.

A grant row grants nothing when its anchor row does not exist. Without this rule, a caller could create a grant for a project key before the project exists, and receive access when someone creates it later.

A grant row also grants nothing when the schema does not declare its role, and every write path refuses an undeclared role. Rows stored before the schema declared a role are the exception: when a registration adds the role, or adds `grant` to an entity that already holds rows, those rows start to grant it. Registration does not scan for such rows, because that reads the grant entity in every workspace on each registration, and the rows were written under the rules of the application at that time. A runtime registration must pass `AllowAccessChange` for such a change, and that flag is where the operator accepts the stored values.

## Teams

A team is a row. The team entity's `members` option names a grant entity whose rows anchor at the team, and each such row makes its subject a member. A grant row whose subject field references the team gives its role to every member. The type of the subject field decides between a user and a team, so one roster entity with a oneof subject holds both, with one list of roles. Two entities would require two lists, because role names are unique across the schema.

**Membership is a row, not a permission.** A permission held at the root applies at every row. If a permission made a caller a member, an admin would be a member of every team and would hold every team's grants. The caller's access set would grow with every team grant in the workspace. A role that does not grant the permission would make no member, and nothing would report it. With rows, a caller is a member of exactly the teams that its own rows name, and the engine finds them in the grant rows it already reads.

**A grant to a team is a delegation.** The subset rule still applies to each row: the writer of a team grant holds the role's permissions at the anchor, and the writer of a member row holds the member role's permissions at the team. A grant to a team also gives its role to every caller who joins the team later, and a caller who can add members does not need to hold that role. This is what a team is for: the project admin decides that the team gets the role, and the team decides who is in it.

**A team cannot be a member of a team.** Grant resolution has two passes. The first pass reads the caller's own grant rows, member rows included, which gives the caller's teams. The second pass reads the grant rows that name those teams. A team inside a team would require a third pass, and nested teams in general require repeated passes with a depth limit. Registration therefore refuses a member entity whose subject is a team. Lifting the refusal later breaks no schema.

The caller's access set stays one list of permissions and anchors, whatever pass found them. Cursors, resyncs, and the `CallerAccess` summary work the same for team grants: a change of membership or of a team grant changes the anchors, and the next pull resyncs the rows below them.

A team row cannot be deleted while a live grant row names it, for the same reason as an access parent: a team created later with the same key would receive the grants.

## Rules

The `access` option of an entity lists rules. Each rule names operations (read, create, update, delete, or `write` for every write operation) and a source: a permission, or `admitted` for every caller that the workspace gate lets in. See [Access model](../reference/proto-options.md#access-model) for the options.

**Rules join with OR.** An operation is allowed when any rule admits it, and the order of the rules has no effect. Rules are monotonic for the same reason as grants: a new rule can only add access. Each rule means the same thing whatever other rules the entity has, and a reviewer can read one rule and know what it allows. On the read side, the rows a caller reads are the union of the rows below the anchors of each read permission, which is the set that a grant change resyncs.

**A rule can need several permissions.** Because rules join with OR, two rules cannot express "`edit_tasks` and `use_billing`". A rule's `requires` lists every permission the caller must hold, and each one holds at the root, at the row, or up the chain. The name says "all of these", so the list does not read as "any of these". Rules with OR and lists with AND together express any rule that only adds access: "`A` and one of `B` and `C`" is the two rules `[A, B]` and `[A, C]`, so the model has no expression tree. The source has no main permission, and the order of the list has no effect. On the read side, the rows such a rule shows lie below an anchor of each of its permissions. A read narrows to the rows below the anchors of every permission that the caller does not hold at the root, and keeps the rows that appear for each of them. A cursor records the anchors of every permission a read rule needs, so a grant or revoke of any of them resyncs. A move compares each such rule on its own, since one permission can stop holding where the others still hold.

**An update needs one rule for both sides.** An update can move a row to another access parent, and a rule admits the move only when its source holds where the row is and where it goes. If one rule could admit the old place and another rule the new place, two narrow rules together would allow moves that neither rule states. For example, a rule for triagers in an intake project and a rule for editors in their own projects would together let a caller with both roles move any intake task into a project that it edits. With one rule for both sides, each rule adds exactly the moves it states.

**A check reads only the row.** A rule can add checks to its source: `caller_is` compares a field with the caller's subjects, `fields` limits what an update changes, and `when` tests a condition on the row, such as "not archived". Each check reads the row that is read or written and nothing else. A change to a field that a check reads is therefore a write to that row, which the change scan sends like any other write: a row that stops matching a read rule reaches its readers as a tombstone, and needs no move log and no resync. A condition on another row, such as "the project is not archived", changes what every row below the project shows without a write to any of them. That is a change of the tree, like a move, and a `within` entry states it. A `when` condition uses the predicate language of queries, so the server and the client evaluate it with the evaluators in `testdata/queryeval` to the same answers. A `rel` condition reads another row and a `match` condition ranks text, so neither can decide access.

**A guard takes a field away from every rule.** A **field guard** is a schema configuration on a field that restricts reading or writing that field across all rules. A rule's `fields` list and a field guard both decide which fields a write may change, in opposite directions. `fields` belongs to one rule and adds a narrow update: an assignee who may set the status, and nothing else. A guard belongs to a field and restricts it whatever rule admits the write: only managers set the status, and only server code sets a total. Each is concise for its own case and verbose for the other. Expressing "only managers set the status" with `fields` lists every other field on every update rule. Expressing "the assignee sets only the status" with guards requires guarding every other field. A guard joins with the rules with AND, and its own rules join with OR, so a guard rule can only add callers to the field that the guard took away. A guard rule's checks read only fields that no guard names, so the answer for one guarded field never depends on the value of another.

**A field the caller may not write keeps its value.** A `PATCH` names the fields it changes. A `PATCH` of a field the caller may not write asks for an unauthorized change, and the server refuses it. A `PUT` names no field: a client sends the row as it holds it, and a field it may not write is often only the value it read. The server keeps the stored value of such a field and applies the rest, on a guarded field and on a field outside the `fields` lists of the caller's rules alike. A client can edit the fields it may write without a read-modify-write cycle that knows the rules. A create stores the zero value instead, so a client cannot seed a value it may not write.

**A guard can hide a field, and the row says so.** A guard's read rules decide who reads its fields, as its write rules decide who writes them. The server clears a hidden field before the row leaves it, on every path that sends a row, and names it in `RowChange.hidden`. A cleared field and a stored zero value encode the same bytes. Without the list, a client could not distinguish "hidden" from "empty", and would show an empty salary, or write the zero back. The list follows the confirmed row on the client, so a local write does not show a field the server hides.

**A hidden field cannot decide what a caller sees.** A predicate, an order, a grouping, or a window over a hidden field answers questions about its value: which rows match `salary > 100000`, in which order, and how many have each value. Treating the field as absent per row does not resolve this, because an index plan, a count read off an index, or a window boundary in the cursor still reads the stored value. The server therefore refuses a request that names a field the caller does not read on every row it reads, which it can decide from the caller's grants alone, before reading a row. A subscription that a client already holds when a grant change hides such a field is not refused, because a refusal would stop sync and leave the rows it selected on the client. It selects no row while the field stays hidden, so the hidden value decides nothing the client holds, and a resync removes the rows it selected. A field a caller reads on some rows only, such as a review its subject alone reads, stays out of queries for that caller. For the same reason, registration refuses to hide a field that a rule checks: a client decides `can()` from the rows it holds, and a guard read rule's own checks read only fields no guard names.

**A field the caller may not read keeps its value on a `PUT`.** A client sends a `PUT` with the row as it holds it, and a hidden field holds the zero value it received. The server keeps the stored value of each field the caller may not read on the stored row when the `PUT` leaves it unset: the caller received it cleared, so an unset field is what it was given, and a set one is a value the caller wrote. A caller that may write a field it may not read, such as a new PIN, sets it either way, and clears it with a `PATCH`. An undo restores what the client held, so it leaves hidden fields out. The undo of a delete of a row with hidden fields is refused rather than recreating the row with zero values.

**A grant change resends the rows whose fields it shows or hides.** Field read rules have the same inputs as row read rules: permissions held at anchors, and checks on the row. The cursor records the anchors of their permissions as it does for row read rules, so a grant change resyncs. The resync compares the hidden fields of each row as well as whether the row is visible. A write that changes what a guard decides on a row is a write to that row, which the change scan sends like any other write. A text field that becomes readable arrives whole, because the client holds no prior state for a delta to apply to.

**A local query reads a hidden field as its zero value.** The client stores the row the server sent, with the hidden field cleared. The server refuses a subscription that names such a field, so the client holds no rows because of one, but an application's own local query can still compare it. Use `Row.hidden`, or `can()` with `fields`, to detect a hidden field.

**An operation that no rule names is left to trusted writes.** The schema states what callers may do, and what it does not state is closed. A server-owned entity is an entity with a read rule only, and an append-only entity is one with a read rule and a create rule. Trusted writes (connectors, effects, mutator bodies) are application server code, and they skip the rules as they skip permission hooks. The operation of a write follows from the write itself: a `PATCH` is an update, a `DELETE` is a delete, and a `PUT` with version 0 is a create. The server refuses an unauthorized write before opening the write transaction, and the client refuses it before it enters the pending queue, where it would fail.

**An entity without `access` is outside the model.** Most entities of a workspace are open to everyone in it, and the model exists for the rest. An entity that declares no `access` stays as it is in a schema without the model: every caller the workspace gate admits reads and writes its rows, application hooks narrow that, and no rule, anchor, or resync applies to them. Declaring `access` on one entity costs nothing on the others, and what a declared entity leaves unstated is closed. The cost is the schema with roles: there the gate admits only callers that hold a permission, and an entity outside the model is open to all of them. This is appropriate for a label, but unsafe for a salary. Registration logs a warning for each such entity, and `WithStrictAccess` turns the warning into a refusal for teams that want every entity stated. An access parent must point at an entity in the model, because the engine checks the deletion and the moves of anchor rows only there.

**`admitted` is a source, not a switch.** Some entities, such as labels, are open to every member of the workspace. `admitted` states this for one rule, so one entity can let every member read and only admins write. The entity stays in the model: it can have an access parent, be the access parent of rows that need a permission, and be a grant entity. A caller is admitted when `CanAccessWorkspace` lets it in and, in a schema that declares a role, it holds at least one permission in the workspace. In such a schema, `admitted` still needs a grant row or a root role for the caller.

**A schema without a role leaves admission to the application.** Rules are useful without grants. A server-owned entity, an append-only log, or a setting that only its owner edits needs no role, and the application often decides who belongs to a workspace in `CanAccessWorkspace` already. In a schema that declares no role, no caller can hold a permission, so the gate cannot ask for one: it admits every caller that `CanAccessWorkspace` lets in, and the rules decide what each caller does. In a schema that declares a role, the grants decide who belongs to a workspace, and the gate refuses a caller that holds no permission even when `CanAccessWorkspace` lets it in. The first role therefore changes who enters every workspace, although no rule changes, and a runtime registration must pass `AllowAccessChange` to declare it.

## Chains of parents

A row's access parent can have an access parent of its own. A comment sits below a task, and the task below a project, so a permission held at the project reaches the comment. An entity can also be its own access parent, as in a folder tree. A caller holds a permission at a row when it holds it at the root, at the row, or at any row up the row's chain.

The engine walks a chain upward from the row, one parent at a time, inside the read snapshot. It reads each row on a chain once per read, so the rows below one task cost one read of the task. For a chain of one level, the walk reads nothing: the row names its parent, and the parent has no parent to read.

To find the rows a caller can read without scanning an entity, the engine walks downward: from the caller's anchors down through the index of each access-parent reference, entering only the entities that lead to the target entity. A guest in one project reads the tasks of that project and the comments of those tasks, and nothing else.

Two limits keep the walks bounded. `Limits.MaxAccessDepth` caps how many rows a chain has: registration refuses a schema whose entities chain deeper, a write refuses a row that would sit deeper in a recursive chain or put a row below it deeper, and a read stops walking at that depth. A write that would place a row below itself is refused on every write path, so the data never holds a cycle.

A row's access parent can also be polymorphic: a comment sits on a task or on a doc. The row still has one parent, and the case it holds decides which entity that parent is a row of, so a chain walk follows whichever case each row holds. The downward walk probes the reference index of each case. Each case has its own index, so a guest in one project reaches the comments on that project's tasks without reading comments on docs.

A polymorphic entity has one set of rules, not one set for each case. The rules that decide whether a caller reads a comment stay the same for the entity, whatever case the comment holds. Moving a comment from a task to a doc changes where it sits, but not what it needs. The cost is that the roles of each tree must grant the permissions of the comment rules. `parents` names the whole oneof, never one member of it: a row that held a case outside `parents` would anchor at nothing, and only a caller with the permission at the root could read it. A change of case is a move like any other, and two targets with the same key are two rows, because a row's parent is always an entity and a key together.

A row can also sit below several rows at once: a task in a project and in a milestone, or a doc in several spaces. The entity names several reference fields in `parents`, or a repeated one, and the row sits below every row they name. A permission held at any of them, or above any of them, reaches the row. This is the rule that applies to one parent, extended to a set: access only adds, so a second parent can show the row to more callers and never hides it from the readers of the first. The rows above a row are a graph, not a chain. A read walks it breadth-first, reads each row once, and finds an anchor on any path of at most `MaxAccessDepth` hops. The downward walk needs no change, because the reference index of a repeated field holds one entry for each element.

A parent is a share. Adding a row below a milestone shows it, and every row below it, to whoever reads the milestone. A caller who edits the task through its project must not be able to show it to an audience it does not manage. A write that adds a parent needs its rule through that parent on its own. Removing a parent hides the row from that audience, and needs the rule there for the same reason. A create adds every parent it names, so it needs the rule through each of them. A rule's `within` entries count the same way: each must pass at the row itself, or at that parent or a row above it. Everything else, such as editing a title or deleting the row, needs the rule through any one parent, as a read does. A move from one project to another is one parent removed and one added, so the rule for one parent is a special case of this one and does not change.

A grant row keeps one parent. It applies its role at one anchor, and the checks that stop a caller from granting more than it holds compare one anchor with another. An application that grants a role at two rows writes two grant rows.

`Limits.MaxAccessParents` caps the rows one row can sit below, because every walk and every move of the row pays for each of them. A row named twice in a list counts once. In a recursive entity, a write checks the longest path above the row, plus the longest path below it, against `MaxAccessDepth`, since a read can reach an anchor through any path and the rows below move with the row.

There is no stored chain. A stored chain for each row would have to be rewritten for every row below a row that moves, under the write lock, and that write would show the keys of those rows to clients that cannot read them. The engine reads the chain when it needs it instead, and records moves in a move log.

## Checks on the rows above

Some rules depend on a row above the row. A private project hides its tasks from the members of the org, who read every other project's tasks through a permission at the workspace root. An archived project makes its tasks read-only for everyone. The owner of a doc reads and edits its comments. A `within` entry on a rule states such a check: the row must be, or sit below, a row of a named entity that passes a `caller_is` or a `when` check.

**One row that passes is enough.** The rows above a row are a graph when a row has several parents, and the entry holds when any row of the entity on any path passes. This keeps parents additive: a second parent can show a row to more callers and never hides it from the readers of the first, as with permissions. A row with no row of the entity above it fails the entry, so a task without a project is not readable through a rule that needs the project to be open. The cost is in recursive trees. A private folder inside a folder that is not private does not hide its documents through such a rule, because the outer folder passes. No `within` entry can make an inner row hide what is below it from the readers of the rows above. A private project works because the project is the only row of its entity above a task: org members read through a permission that the entry checks, and project members through one that it does not.

**An owner is a check, not a grant.** "The owner of a doc reads its comments" could be a grant row for each doc, anchored at the doc. Then the caller's access set would grow with every row the caller owns, and so would every cursor record and `CallerAccess` summary. A `within` entry with `caller_is` reads the owner field of the doc while it walks up from the comment. It costs one read of the doc when its comments are read, and adds nothing to what the caller holds. An owner field also has no subset rule, so the rules of the doc entity decide who can change it.

**A change of a field that an entry reads is a change of the tree.** When a project becomes private, no task is written, but every task below it changes visibility. The engine therefore treats the write the way it treats a move: it records the write in the move log, with what the entries read of the row before the write. The next pull compares, at that row, what each read rule of the entities below admits before and after. A caller can hold a permission at a row below the changed row, such as a grant on one task, so the comparison also considers the anchors that can sit below the row. A write that changes what an entry reads of a row also needs the right to read the entities below it, where the row is, because it can show those rows to other callers, just as a move to another parent can.

The engine reads only the fields of the row of the named entity, and only when a rule needs them. A `when` condition there uses the predicate language of queries and reads that row alone, as the `when` of a rule reads the row itself.

## Reads use one snapshot

Every read path filters returned rows with the caller's grants as of the same read snapshot: Pull, Bootstrap, Subscribe, Query, `View`, and `Apply`. Reads never mix grants from two points in time. For example, a grant written in the same transaction as a task never reaches the client before or after that task. In a schema that declares a role, the workspace gate refuses a caller that holds no permission in the workspace before reading or writing rows.

## Writes are checked inside the transaction

A write requires a rule that admits its operation where the row sits. The engine checks this inside the write transaction, so a write sees the grants that earlier writes of the same batch made. The transaction evaluates grants again after a write to a grant row or to a row that can be an anchor:

- An update or delete is checked against the stored row, before the version check, so a refused caller does not learn the row's version.
- A `PATCH` or a `DELETE` of a row that does not exist receives `access_denied`, with no tombstone, matching the response for a row the caller cannot change. Otherwise the answer would reveal which keys exist, and any caller could write tombstones that reach every reader. A write to a row that the application's `ReadFilter` hides receives `access_denied` for the same reason. A client that deletes a row that another client deleted first gets a rejection.
- A create is checked against the new row after merges, carried-over fields, and reference projection.
- An update that moves a row to another parent is checked at both parents, by one rule. Otherwise a caller could move a task into a project it can write and out of one it cannot.
- On a row with several parents, an update that adds or removes a parent is checked through each parent it adds or removes, and a create through each parent it names, by the same rule.

A move shows the moved row to whoever reads at its new parent, the mover included. A move therefore requires, where the row is before the move, the right to read the row and each field of it that a guard can hide. Without that rule, a caller who may edit a staff record but not read its salary could move the record to a project where it reads salaries.

This applies only to a field whose readers depend on where the row sits: a read rule of its guard requires a permission, which a caller holds at a row up the chain, or sets a `within` entry. A field that no client reads, or that only the caller the row names reads, such as a review that only the person it is about reads, has the same readers at every parent. The move shows it to nobody new, so the mover does not need to read it. Without this exception, a field that no client reads would stop every client from moving the row, including a caller that holds every permission at the root. A move that changes a field that such a read rule checks, for example a `when` condition on the access parent, changes who reads the guarded field, and the rule below applies to it.

A move also carries every row below the moved row with it. A move therefore also requires, where the row is before the move, a read rule of every entity whose rows can sit below it that reads every row. A rule with a `caller_is` or a `when` check reads some rows only, so it does not count. Without that rule, a caller who may edit tasks but not read their comments could move a task to a project where other people read comments, and a caller who reads only its own comments could move the comments of other people. The same exception applies: an entity below, or a guarded field of it, whose readers do not depend on where its rows sit needs no read rule from the mover. Comments that only their authors read, wherever they sit, have the same readers after the move.

A caller can move a row into a subtree where it holds a wider role than where the row was, and then change the row there in ways it could not before, for example delete it. The model allows this. The move needs a write rule at both ends, so the caller can already change rows at the source and at the target. The read checks at the source make sure that the caller already reads the moved row, each field of it that a guard can hide from a reader at the target, and every row below it that a reader at the target can read. The move therefore shows the caller nothing that it could not already read, and the wider role applies only in a subtree where the caller already writes. To keep a row in its subtree, do not give the caller a write rule that admits moves out of that subtree.

A field that a guard's read rule checks with `caller_is` or `when` decides who reads the guarded fields. An update that changes such a field requires the right to read the guarded fields before and after the update. Without that rule, a caller who may edit a staff record could set its `person_id` to itself and read the review written about another person.

A client cannot delete a row while a live row names it as an access parent, also when that row has other parents. If it could, the rows below would anchor at nothing, and a caller who creates a row with the same key later would take them over. Trusted writes may delete such a row, because a connector or a mutator body sometimes must. The rows below it then anchor at nothing until a row with that key exists again. For the same reason, a client cannot create a row while a live row names its key as an access parent, or a live grant row names it as its subject: the create is refused with `conflict`. Otherwise the new row would take over the rows left below the old one, and a stale grant would hold its role again. A trusted write can create such a row, and the rows that name it then sit below it. The message of such a refusal does not name the entity of the rows below, which the caller may not read.

In a recursive chain, a write that adds an access parent also requires the right to read that parent, and a parent that does not exist is not read. The depth and cycle checks read the rows above the new parent, so without this rule their answer would tell a caller where a row it cannot read sits.

Trusted writes skip the rules, but not the engine's own bookkeeping: the move log, the cycle check and the depth check. While a run of `RegisterEntity` calls leaves the model incomplete, that bookkeeping uses the last model that compiled, so a move in that window still reaches the next pull and a cycle is still refused.

Grant rows have a further rule: a write that can change what a grant row grants requires every permission of the role at the grant's anchor, before and after the write. A caller can therefore only grant or revoke what it holds itself. This stops a caller from raising its own role, from giving a grant to another subject by changing the subject field, from moving a grant to a project it does not manage, and from demoting a caller with a stronger role.

A custom mutator writes rows that the engine does not check one by one. In a schema that uses the model, an invocation requires a `MutatorAccess` that names the permission and the row it is checked at, or it is refused. The body applies the model to a write by writing through `EntityTx.AsCaller`, which checks it as the caller's own write, and can ask `EntityTx.Can` about a permission. Reads follow the same split. The body is server code, so its own reads see every row. Its reads through `AsCaller` read as the caller's client would, so a body that passes on what it reads, for example in a rejection message, shows the caller only what the caller can read. Mutators stay unchecked by default because some writes must break the subset rule on purpose, for example making the creator of a project its first admin. A mutator cannot admit a caller to the workspace: in a schema that declares a role, a caller that holds no permission in the workspace is refused before any mutator runs.

## How changes of access reach clients

When a grant changes, the visibility of rows changes without a write to those rows, and a pull from the old cursor would not find them. Each cursor therefore records what its caller could read: the read anchors per permission, and a reference to the record in the cursor-state store.

On the next pull, the engine compares the caller's current read anchors with the record:

- The same anchors: the pull continues as usual.
- Different anchors: the pull starts a resync. It reads only the rows below the anchors that were added or removed, through the reference index, and sends rows that became visible and tombstones for rows that became hidden.
- An entity that the caller could read at the root and now cannot: the resync drops the entity on the client and sends the rows the caller can still read. This costs what the caller keeps, not one tombstone for each row it lost.
- A change to the access model: the record also holds the read rule of each entity, which is who its read rules admit and its access parent, and an entity outside the model reads as open. If an entity that the record and the current schema both know has a different read rule, the rows on the client were chosen by a rule that no longer applies, so the client resets and bootstraps again. An entity that joins or leaves the model is such a change. Other model changes keep the cursor. A role that grants other permissions moves the anchors, which resync as above. An entity that is new to the schema has no rows on the client to correct. Thus a client can move between nodes with the older and the newer schema during a rolling deploy, and it does not reset.
- A change of `Limits.MaxAccessDepth`: a lower limit hides the rows below the chains it cuts short, which no anchor and no move names, so the client resets.
- A missing record or a cursor issued to other subjects: the client resets and bootstraps again.
- An unconfirmed or invalid cursor: the client resets and downloads the workspace again (bootstraps). When the caller holds no permission, the server refuses the request.
- No permission at all: the gate refuses a caller that holds none. A pull from a cursor whose record holds a permission first runs the resync to the empty set, which tombstones every row the caller read and sends a summary that holds nothing, as an open stream does before the gate drops it. The pull after it gets the refusal. A cursor that never held a permission gets the refusal at once, so a caller that waits for its first grant keeps what it has.

When a caller loses access, the next pull removes the rows it can no longer read. Active clients that keep syncing under unchanged grants do not expire. Changes to application code that do not change schema rules preserve existing client cursors.

### Moves

A move changes visibility without a grant change. When a task moves to another project, every comment below it changes visibility, but no comment is written, and neither the grants nor the change scan show it. The engine therefore keeps a move log: every write that changes the access parent of a row of an entity that rows can sit below, changes what a `within` entry reads of such a row, or deletes such a row, records the row, its parent and what the entries read of it before the write, in the same transaction. It does so whether or not rows sit below the row at the time of the write. A matter can move out of a dossier, and the dossier can then turn private: nothing sits below the dossier at the second write, but the memos of the matter sat below it when the client's cursor was issued, and the pull decides what the client holds by walking their old chain through the dossier as it was then. Only the log holds that. A create is recorded only when rows below already name the row's key, and a row created after the cursor is treated as not yet existing on the old side.

On the next pull, the engine reads the moves after the cursor. For each moved row it compares the chain above the row as the client's rows reflect it with the chain now. If a read rule of an entity below the row admits the caller on one side and not on the other, the pull resyncs the rows below the moved row, sending rows that became visible and tombstones for rows that became hidden. A move that changes nothing the caller reads, such as a task moved between two projects the caller is not in, costs that caller one read of the log. After the resync the cursor records the newest move it reflects, so the next pull does not resync the same moves again.

During bootstrap, the engine delivers only rows the caller is currently permitted to read, even when rows move while pages are fetched. If rows move during bootstrap, the subsequent pull synchronizes the changes.

A move during a resync resets the client when it changes what the caller reads, as a grant change during a resync does. A cursor that has more moves after it than `Limits.MaxResyncScan` also resets, and a Bootstrap that resumes from such a cursor begins a new snapshot instead. Garbage collection removes moves at or below the tombstone horizon, where every cursor resets anyway.

## What the client knows

The client receives a `CallerAccess` summary: every permission the caller holds and its anchors. To answer for a row below an anchor, the client walks the row's chain through the rows it holds locally, its own queued writes included. When a row of the chain is not held locally, for example a task the caller cannot read above a comment it can, the client reads the schema: if the caller holds the permission at no row of an entity that can sit above that row, the answer is `'no'`, and otherwise `'unknown'`. Rows do not carry the keys of the rows above them. This keeps unreadable rows off the client, and a move sends only rows whose access changes. The cost is that the client cannot answer `'yes'` through a row it does not hold.

The server sends the summary when it changes, and the client stores it with the cursor. For a caller with grants at thousands of rows, one more grant would resend every row, so a pull sends only changed rows as a delta from the summary version the client holds. Each summary has a version, and each pull and stream names that version. A delta names the version it applies to, because tabs that share a store pull simultaneously. The client applies a delta only to the summary it names. When the store holds another summary, the client keeps it and pulls again. Predictions use the older summary for that one round trip. `can()` and `useCan` answer `'yes'`, `'no'` or `'unknown'` from it.

The answer is advisory. The client does not refuse a write when `can()` answers `'no'`, because the answer depends on rows and grants that the client may not hold. It refuses only a write that no rule admits to any caller, which it can tell from the schema alone. Every write is queued, and a refused write comes back as a rejection acknowledgement. A row the caller lost access to keeps showing a pending local write until that acknowledgement arrives.

## Costs and limits

- **Grant resolution.** Each request and each stream drain reads the caller's grant rows: one probe of the subject index for each grant entity, or a scan of the grant entity until the index is built. Team grants add one probe of the team reference index for each team the caller is a member of, and a read of the grant rows found.
- **Chain walks.** A read below the root reads each row on the chains of the rows it classifies once. A write reads the chain of the row it writes, and a move of a row in a recursive chain reads the rows above the new parents to refuse a cycle and a path deeper than `MaxAccessDepth`. It also walks the rows below the moved row, level by level through the reference index, up to the depth that the path above leaves. A create of an anchor row probes the reference index of each entity that can sit below it, as a delete does. A row with several parents costs a walk of each of them.
- **Moves.** A move of a row that rows sit below writes one log row. Every pull and stream drain reads the moves after its cursor, which is one row read when nothing moved. A delete of such a row probes the reference index of each entity that can sit below it.
- **Root changes.** Gaining or losing a permission at the root affects every row of the entities that use it, so the resync scans those entities.
- **Shared permission names.** A permission used at two depths that do not sit below one another, such as `view_members` for org members and for project members, lets a role that grants it at the root read the rosters of every project. Registration logs a warning for this case. A permission shared by a row and the rows below it, such as `view_tasks` for tasks and their comments, is the common case and logs nothing.
- **Tombstones reveal keys.** A tombstone for a hidden row still shows the row's entity, key and version. Use keys that are not secret.
- **Versions reveal when a hidden field changed.** A write that changes only fields a guard hides from a caller still gives the row a new version, and the change scan sends the row to that caller again: with the hidden fields cleared and nothing it reads changed. The caller learns when such a field changed, and a `byRecency` window orders by that version, but the value stays hidden. The row keeps one version for every caller because a write with an expected version compares it with the stored version. A client that did not receive the new version would have each such write of the row refused as stale until a field it reads changed. Put a field whose time of change is sensitive in an entity of its own, whose read rules hide the whole row.
- **Text deltas.** A caller below the root receives collaborative-text edits as deltas. A write that moves a row to another access parent, changes a field a read rule compares with the caller's subjects, or changes whether the row matches a read rule's `when` condition, sends the row's documents whole once to every reader whose next pull covers that write.
- **Checks above.** A read that classifies a row through a `within` entry reads the rows above it of the named entity once per read, through the same cache as the chain walk. A row of an entity without an access parent is read only when an entry names its entity. A change of a field that an entry reads of a row that rows sit below writes one move-log row, and every pull and stream drain compares it as it compares a move. A caller who holds the rule's permissions at the root, or a rule with `admitted`, narrows only through an entry's `caller_is` field when that field is indexed; otherwise the read tests every row of the entity.
- **Conditions.** No index finds the rows that match a `when` condition. A read narrows by the rule's anchors and tests each row it reads, and a caller who holds every permission of the rule at the root, or a rule with `admitted`, reads every row of the entity. A resync after such a permission moves to or from the root scans the entity.
- **Query.** For a caller below the root, the `Query` RPC reads only the rows below the caller's anchors, which it finds through the reference index, and an index walk skips the entries of other rows without reading them. When the caller has more such rows than `MaxIndexScanCandidates`, the query reads like one from a caller at the root: through an index walk or a scan of the entity, with the model as a filter.
